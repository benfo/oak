# Oak — a modern Git GUI (GitExtensions alternative)

Electron + React 19 + TypeScript, built with electron-vite. Runs the user's installed `git` CLI
(never a git library) so hooks, credentials, config and LFS behave exactly like the command line.
Primary platform: Windows 11.

## Project goals
- **Consistency and user joy:** Oak should feel modern, simple, dependable and a pleasure to use. Judge features by how easily people complete everyday Git tasks, not by the number of tools or controls.
- The same action should have the same keyboard, mouse, selection, focus and feedback behaviour across views. Navigation preferences add alternatives without changing search, selection or action semantics.
- Make frequent actions quick and discoverable; keep occasional controls contextual. Preserve the user's place and selection, avoid layout shifts, and make the current state clear. Do not add permanent UI or commands without a concrete workflow benefit.
- Treat confusion, unnecessary steps and frustrating interactions as product issues. Work in small, locally reviewable experiments and use the user's testing to decide what stays.
- Prefer fewer permanent actions over a configurable toolbar by default. Fetch/Pull/Push stay visible; occasional actions belong in contextual menus and the command palette. Add customisation only when a concrete everyday workflow demonstrates the need.
- Website demonstrations show a small, useful feature set using real shared UI where practical. Keep examples independent and resettable, and put feature-switching controls/instructions outside the app frame. Do not recreate the whole client or share simulated repository state across unrelated examples. Explain concrete outcomes; omit demo modes that obscure the feature's value without removing desktop functionality.
- Visual direction: original, modern, focused and uncluttered, with Linear/Raycast as references rather than templates to copy. Flat styling is welcome. Describe Oak as cross-platform while stating actual package availability and testing honestly; Windows is primary, Linux experimental, macOS untested.

## Commands
- `npm run dev` — run with hot reload (main-process changes need a restart)
- `npm run build` — production build to `out/`
- `npm run typecheck` — `tsc --noEmit` (run after every change)
- `npm run lint` — stylelint: CSS must use design tokens (see "Design system")
- `npm test` — Node test runner over `tests/**/*.test.ts` (runs TS directly; tests use real git in a temp repo)
- `npx electron . <repo-path>` — open a specific repo (after `npm run build`)
- `npm run dist` — Windows installer in `dist/` (`Oak-Setup-<version>.exe`; per-user, Start menu + desktop shortcuts, Explorer "Open with Oak", `oak` command via `%LOCALAPPDATA%MicrosoftWindowsAppsoak.cmd`; extras in `build/installer.nsh`). `dist/win-unpacked/Oak.exe` runs without installing.
- `npm run dist:linux` — build x64 AppImage and Debian packages on Linux. `xvfb-run -a npm run test:linux-package` verifies the installed `/opt/Oak/oak` UI and real Git staging in an isolated repository/profile, with the sandbox enabled.
- `npm run icon` — re-render `build/icon.png` from `build/icon.svg`
- `npm run release` — publishes complete prebuilt Windows/Linux assets from `dist/` after validating updater hashes (token from `gh auth token` or `GH_TOKEN`). Normal releases use the tag-triggered Release packages workflow, which builds on native runners and tests the installed Debian app before publishing. Bump `version` and add release notes first. Installed copies check `benfo/oak` (`src/main/updater.ts`, electron-updater), download in the background and offer "Restart now" (`components/UpdateNotice.tsx`); Preferences → General → Updates. Dev builds report "unsupported".

## Design rules (agreed with the user — follow them)
- **No layout shift.** Transient UI (status, progress, selection bars, hints) uses reserved space or overlays; never pushes content under the mouse. Delay progress UI ~300 ms so fast ops don't flash. Keep button widths stable while busy.
- **Focus indicators are one system** (`styles.css`, "focus indicators"): controls and text fields get a 2px `--focus-ring` outline outside. Panes are wrapped in `.pane-frame`, which draws the ring as an overlay above the pane's content, only while the pane has `data-focus-ring` (set by `lib/focusRing.ts` when focus *arrives* by keyboard; a click clears it; arrows inside don't change it); list panes sit 4px inside the frame (an outline on a scroller gets covered by sticky/virtualized children); rows show focus with a tint + 3px accent bar, never a ring hugging text; the diff cursor is an overlay above the sticky gutter. High-contrast mode (`forced-colors`) gets real outlines. Mouse clicks on panes/buttons don't show rings (`:focus-visible`). New scrolling panes go inside a `.pane-frame`.
- **Row padding:** every list row uses `--row-pad` (10px) both sides; nesting adds `--indent` (20px per level).
- **Tokens only.** No raw colours, spacing, radii, font sizes or control heights in CSS or components; use `tokens.css` (see "Design system"), `npm run lint` checks.
- Ctrl+A is scoped to the focused pane (`App.tsx`), never the whole page.
- Disabled buttons look inert; explain *why* something is disabled in visible text (disabled buttons can't show tooltips).
- **Menus:** large lists you pick from (branch, repo) are searchable pickers dropping down from their toolbar button (`pickers.ts`, palette with `anchor`); small action menus are React Aria `Menu`s (Pull options); right-click menus are React Aria menus too (`showMenu` → `components/ContextMenu.tsx`: at the pointer for a right-click, under the focused row from the keyboard, with separators/checks/submenus). Never open a menu at a stray mouse pointer.
- **Pickers preview live:** moving onto a choice (theme etc.) previews it immediately; Enter keeps it, Escape reverts. Theme pickers never dim the app (`see-through` backdrop). Palette supports this via `onHighlight` / `onCancel` / `seeThrough`.
- **Dialogs are keyboard-first:** initial focus lands on something arrow keys can drive (e.g. Preferences opens on its category list).
- **Explicit diff selection:** a click selects exactly the displayed line; Ctrl-click/Space toggles that line. Do not infer replacement pairs or moved-line partners. Select both deletion and addition explicitly when replacing or moving a line. Visual alignment and word highlighting must not silently expand selection. Partial operations preserve line order and leave unselected changes untouched.
- **Immediate, accurate feedback:** refresh the working diff after content changes even when Git status codes stay identical. Preserve stable list state and unchanged previews; never leave a successful operation looking like it did nothing.
- **Interactive examples look interactive:** label them clearly, provide breathing room around the app frame, and give a concrete first action. Keep instructions and Reset outside the frame; reuse shared app behaviour so demonstrations include its fixes.

## Keyboard model
- Search is explicit in both navigation schemes: / or Ctrl+F searches the focused list. Persistent branch/history search fields keep focus while Enter/Shift+Enter find next/previous matches; Escape returns to the match in the owning list and retains the query. These search inputs are excluded from Tab stops; /, Ctrl+F, Ctrl+L (branches) or a click deliberately enters search. Tab from search enters its owning list; Shift+Tab goes to the preceding pane. F6/Shift+F6 cycle relative to the owning pane (data-search-pane). Choice pickers, including file find and command palettes, use Enter to accept and close and Escape to cancel. File pickers select and focus the found row (including off-screen virtualized rows); they never stage/unstage or move into the diff. Enter or Right from the list performs the existing action. Plain typing does not start search or jump in lists. Optional Vim-style navigation (Preferences > General, off by default) adds plain h/j/k/l alongside Left/Down/Up/Right in sidebar, graph, file lists and diffs. Ctrl+D/U moves half a viewport and gg/G goes to the first/last item or line in the focused list or diff; these do not switch files while code has focus. gg requires two deliberate presses within one second on the same focus target; other keys, pointer interaction and leaving the pane cancel the prefix. Menus retain only h/j/k/l. Text fields, other modified shortcuts, arrow navigation, selection/action keys and diff N/P retain their existing behaviour. lib/useNavigation.ts adapts these motions into existing arrow/Home/End/Page handlers; GridList uses built-in disallowTypeAhead. No Vim editing modes. Ctrl+Shift+P still opens commands in either scheme.
- Tab / Shift+Tab use native/React Aria traversal: collections have one stop, forms retain their ordinary controls. Pane tools (fixed header/footer controls such as Stage all, Copy hash, the All files/Changes toggle, the selected-lines bar) are real Tab stops in visual (DOM) order; per-item buttons (hunk Stage/Discard, row actions, tree chevrons) stay out of Tab because the widget's own keys cover them. Search fields stay out of Tab. F6 / Shift+F6 are the only pane-jump keys (`[data-pane]`), including when focus is on an owned header tool or form control. Escape on a pane tool returns to its owning pane (`handleToolNavigation`, attached through `ownerProps`; keys inside the pane, menus and text fields keep their meaning).
- In lists: ↑↓ Home End PgUp PgDn move; **Space selects, Enter acts** (stage/unstage/open); Delete discards; Shift+F10 / Menu key = context menu; Ctrl+A selects all; use / or Ctrl+F for explicit search.
- The All files tree (History) is a tree: arrows only move, expand and collapse inside it (Left at a root row and Right on a file do nothing); Enter opens a file, Escape clears the filter then returns to the graph. The All files / Changes mode is in-memory (`lib/commitFilesMode.ts`) and resets to Changes on launch, when another commit or comparison is selected, and when leaving History.
- Right opens the focused file's diff; Left/Escape return from Changes file lists to the sidebar. In history, Right/Enter goes deeper (graph → commit files → diff). Enter in Changes file lists retains stage/unstage semantics. In a diff, Left traverses split columns before returning to its file list; Escape clears line selection before backing out. Empty panes support the same back action. Moving between panes preserves selection; entering a diff uses the focused file rather than a retained preview from another section.
- Diff: line cursor, Shift+↑↓/Space/Ctrl+A select lines, Enter stage/unstage, Delete discard, N/P hunks.
- Diff horizontal scrolling: Shift+Left/Right in both schemes; Vim also adds Shift+H/L. Scroll a quarter viewport per press (native repeat while held), using only the active column in side-by-side or the diff scroller in inline. Keep focus, cursor and selection unchanged, including at scroll boundaries. Unmodified arrows/hjkl keep their navigation meaning; Escape keeps its existing selection-clear/back behaviour. Shortcuts are listed in the searchable help.
- Ctrl+Shift+D toggles the visible diff between Inline and Side by side in either navigation scheme; D is the mnemonic for diff. From Automatic, switch to the opposite of the resolved layout and save that explicit choice; restore Automatic through the existing layout menu or Preferences. The command registry supplies palette/help labels. changeDiffLayout.ts is the shared entry point for explicit layout changes (shortcut, menu, Preferences), preserving the visible code anchor/offset and horizontal position without changing focus, cursor or selection. Do not bypass it with a direct settings update for a layout control.
- Global shortcuts live in `RepoView.buildCommands`; Ctrl+/ shows the cheat sheet (`Palette.tsx`).
- **Shortcut scopes:** application shortcuts go through one dispatcher (`lib/shortcuts.ts`; React adapter `lib/useShortcuts.ts`). `useShortcutRoot` (App.tsx) is the only app keydown listener; scopes register with `useShortcutScope` (`app`, `workspace` priority 10, `welcome`) and the last mounted wins at equal priority. Overlays (dialogs, menus, pickers) call `useShortcutOverlay`, a modal barrier that blocks lower scopes except bindings with `allowInOverlay` (F6, select-all). Commands become bindings via `commandBinding`; `Ctrl` in command keys means the platform primary modifier. Text inputs keep their keys unless `allowInInput`. A disabled binding still owns its key (no fallthrough) and its `disabledReason` (`lib/shortcutPolicy.ts`: expanded layouts, busy Git) is shown as a toast. Forms use `handleShortcutBindings` locally. Child/RAC handlers keep first refusal; component-level navigation stays in `lib/navigation.ts`. Add shortcuts as bindings, never new `window` keydown listeners.
- **Key ownership (one rule):** text fields own text editing; the focused widget owns moving/selecting inside itself; commands (anything changing the app, repo or layout) belong to the dispatcher, which only sees keys no widget consumed. Widget keys are declared as data in `lib/keymap.ts` (`WIDGET_KEYMAP`: action → keys per role `list`/`graph`/`diff`, optional `help` shown in the shortcuts dialog). Components call `widgetAction(event, role, shortcutPlatform())` or the `navigation.ts` helpers built on it and supply only what each action does; never test `ctrlKey`/`altKey`/`key` combos in a component. `useShortcutScope` logs (dev) any command overlapping a widget key unless it sets `widgetFallback` (Ctrl+F Find and Ctrl+A select-all are intentional fallbacks). The Find command starts a list's own search through `requestPaneSearch`. Ctrl/Alt/Meta letters match the physical key; plain and Shift letters (N, P) follow the layout. Modules tested by Node import siblings with `.ts` extensions (`allowImportingTsExtensions`). New widget keys: add a `WIDGET_KEYMAP` entry (and `help`), then a test in `tests/shortcuts-keymap.test.ts`.
- **Split resizing:** `Split.tsx` wraps `react-resizable-panels` Group/Panel/Separator; the library owns pointer resizing, bounds and separator ARIA. Keep the first panel's pixel size (`groupResizeBehavior="preserve-pixel-size"`) and existing `split:<id>` localStorage keys. Persist only completed user interactions, converting the callback's committed percentage to available pixels; the imperative panel size is stale during that callback. Each split requires a descriptive `label`. Shift+Alt+arrows (`lib/paneResize.ts`) move the nearest enclosing divider on that axis in the arrow's direction, like Windows Terminal; each `Split` registers a controller and persists its own size, collections handle the chord in `useNavigation` before RAC reads it as selection extension, and a clicked divider keeps its own arrows/Home/End and Escape. There is no Resize panes… picker. Dividers stay out of sequential Tab order via `elementRef`; `handleResizeNavigation` preserves Oak's F6/Shift+F6 owner semantics and guards modified/IME resize keys before the library's native handler. Do not add collection Vim aliases or automatic collapsing to dividers.
- **Workspace layouts:** F11 and the visible expand/restore toolbar button expand the code area (from any pane, focusing the diff) and restore the previous layout/focus. Expansion is temporary RepoView state; saved split dimensions and sidebar visibility stay unchanged. The toolbar has two direct toggles, expand/restore and Sidebar (no Layout menu or Customize layout picker); the named layouts and the expanded history layout were removed from menus and the palette. Resize shortcuts are disabled while expanded with a visible explanation. No docking or saved layout editor.
- **Sidebar and focused-pane visibility:** the toolbar Sidebar toggle and Show sidebar / Hide sidebar commands share `sidebarHidden` (app-wide and persisted); Ctrl+B keeps its branch-picker meaning. Hiding a focused sidebar moves focus to the active main list, falling back to the toolbar for empty history; toggling from another pane preserves focus and selection. Ctrl+L and Changes file-list Left/Escape reveal the normal layout/sidebar before navigating there. Hidden content stays mounted but hidden/inert, and its divider is hidden/disabled. `Split.collapsed` hides the first pane; `restCollapsed` hides the second and expands the first. Both suppress preference writes and restore saved sizes from the panel's resize notification after new constraints settle. Reapply the divider's negative tabIndex when re-enabling it. Do not add automatic drag collapse.
- **Expanded navigation:** the only expanded layout is Code. F11 restores the original layout and focus, and so does Escape once no widget has anything to undo (filter, line selection); that is a dispatcher fallback command (`restore-workspace-layout`, `widgetFallback`), not a widget handler. Left/Right never restore hidden panes; split-column movement and selection clearing retain their meanings. History always opens commit files, then the diff, with Enter/Right. Ctrl+1/Ctrl+2 retain Code expansion across Changes/History. Explicit file/message/graph/search commands reveal their owning panes before focusing them. F6/Tab skip hidden/inert areas. Switching layouts must preserve selections, the current preview and Git state; never let the Escape fallback pre-empt a widget's own selection/back semantics.

## Navigation architecture
- **One policy module:** `lib/navigation.ts` defines common key meanings, modifier/IME guards, custom-list movement, persistent search handling, pane focus/cycling and horizontal diff scroll keys. Add shared rules here rather than copying key checks into components.
- **One React adapter:** `lib/useNavigation.ts` supplies capture-phase explicit search, typeahead suppression and optional Vim aliases for collection panes. Lists use the default; diffs use `{ kind: 'diff' }` to retain N/P. Context and dropdown menus use `MenuNavigation`, which applies `{ kind: 'menu' }` without list search/typeahead suppression. Menu j/k move, l opens a submenu and h closes it; React Aria owns movement, disabled-item skipping and focus restoration. Searchable pickers and forms keep normal typing. Attach the adapter before component-specific keys. Aliases re-enter existing arrow/Home/End/Page handlers so RAC retains virtualization and selection anchors. usePane resetProps must sit on the DOM capture boundary to cancel pending gg on blur/pointer input; RAC collection components filter these capture props. Virtualized collections use NavigationListLayout for the half-page alias; the library still owns destination calculation and selection.
- Use `handleNavigation(event, { activate, deeper, back, dismiss, discard, menu })` for supported common actions. Omit unavailable callbacks; unsupported actions pass through. Native controls, modified shortcuts and composition keep their own keys. Picker/filter inputs must explicitly opt into `allowTextInput`; persistent find fields use `handleSearchNavigation` instead.
- Components own Git operations, selection and scroll geometry. RAC owns collection selection/arrow movement, menu keyboard behavior, and dialog/picker focus containment/restoration. The custom graph and diff use shared key policy with their own domain logic. No global handler should override a child that already handled an event.
- `NAVIGATION_COMMANDS` in `commands.ts` is the single registry source for app-wide F6/Shift+F6, palette and shortcut help. Pane cycling stays within the active overlay and skips hidden/inert panes; Tab uses native/RAC traversal except the deliberate search-to-list transition.
- Pane tools and forms declare `data-pane-owner` with their existing pane's ID; persistent search uses `data-search-pane`. Resolve F6 relative to that owner without adding tools as extra panes. Keep collection navigation out of text editing and preserve modifier/IME guards.
- New areas must choose their role (collection, persistent find, choice picker, native form) and reuse the matching handler. Consistency means shared semantics appropriate to that role, including ordinary text editing in forms; do not apply collection Vim aliases inside controls or dialogs indiscriminately.
- **Pane composition:** Changes, History and the sidebar use `lib/usePane.ts` and `components/Pane.tsx`. `usePane(id, { kind })` binds `targetProps` to the actual collection/custom focus target and `ownerProps` to its surrounding tools; call `pane.navigate(event, search)` before surface-specific capture handling. `PaneFrame` supplies the existing focus-overlay wrapper without adding a Tab stop or scroller. `PaneSearch` supplies persistent-find ownership and Enter/Escape/Tab handling; pass `onFind` and `onLeave`. Keep React Aria collection focus/selection, custom pane refs/roles/tabIndex, Git actions and scroll geometry in their surfaces. Pane bindings are stable per ID; keep the sidebar's memoized tree and row cache intact. Keep `focusRing.ts`'s keyboard-arrival rule. Additional layouts beyond the agreed focused history/code views need a concrete workflow before implementation.

## React Aria (react-aria-components)
Used for the Changes file lists (`GridList`, multi-select, `selectionBehavior="replace"`) and the sidebar (`Tree`), both inside `Virtualizer` + `ListLayout`; the toolbar (`Toolbar`, adds Home/End via `toolbarHomeEnd`); dialogs (`ui.tsx` `Modal` = `ModalOverlay`/`Modal`/`Dialog`); and the palette (`Autocomplete` + `ListBox`, our own fuzzy ranking). The commit graph and diff stay custom. Style via `data-*` state attributes (`data-selected`, `data-focus-visible`, `data-hovered`…) mapped onto our CSS variables. Lessons:
- Our extra keys (→, Delete, Shift+F10, typing-to-filter) go in a **capture-phase** handler on a wrapper so they run before React Aria.
- Items don't take `onFocus`; listen on a wrapper and read `[role=row]`'s `data-key`.
- Type-to-jump moves focus without selecting — `ChangesView` makes selection follow plain-key focus.
- Controlled selection: pass React Aria's `Selection` object back unchanged (it carries the Shift+click anchor); selections you create yourself must be that class too (`anchored()` in ChangesView). Rows rendered from `items` are cached: give `dependencies` or read changing state through a ref, or handlers go stale.
- Virtualized rows sit in sized wrappers: make `[role=row]` and its gridcell `height: 100%`; put spacing inside the row.
- RAC `Button` drops `title` (no tooltips) — use native `<button>`s where a tooltip matters (toolbar).
- **Big collections** — palette: virtualized `ListBox` with an explicit height, matching on text lowercased once per picker, highlights computed only for visible rows, results from `useDeferredValue(query)`. Sidebar (~10k refs): RAC rebuilds its collection synchronously on every render of the Tree, so: leave collapsed sections' children out (handle →/← for them yourself: `hasChildItems` doesn't reach the keyboard), cache row elements per data object (React skips identical elements), memoize the whole `<Tree>` element, and drive cheap visuals (chevrons) from context so they don't re-render the tree. Measure with the dev helper (`performance.now()` around a click + frame).
- A dialog that opens another (palette → prompt) must close synchronously (`flushSync`) and refocus its opener first, or the second dialog restores focus to a removed element.

## Design system (tokens)
All raw values live in `src/renderer/src/tokens.css`; component CSS (`styles.css`) uses tokens only, enforced by `npm run lint` (stylelint + `declaration-strict-value`: colours, spacing, radius, font size/weight; allowed literals `0`, `1px`, `auto`, `transparent`, `inherit`, `none`, system colours, `vh/vw/%`). If no token fits, add one deliberately rather than a raw value. Modelled on shadcn/ui and HeroUI (we borrow the ideas, not the libraries).
- **Spacing** (4px steps, Tailwind names): `--space-0-5` 2 · `-1` 4 · `-1-5` 6 · `-2` 8 · `-2-5` 10 · `-3` 12 · `-4` 16 · `-5` 20 · `-6` 24 · `-8` 32 · `-10` 40 · `-16` 64 · `-20` 80. Rows: `--row-pad` (10) both sides, `--indent` per nesting level.
- **Radius** (one knob `--radius` = 6px): `--radius-xs` r−4 · `-sm` r−2 (badges, kbd) · `-md` r (controls, rows) · `-lg` r+2 (menus, popovers, cards) · `-xl` r+6 (dialogs, palette) · `-full` (pills, dots, avatars).
- **Type**: `--text-xs` 11 (labels, badges) · `-sm` 12 (secondary, code/diffs) · `-md` 13 (body, default) · `-lg` 15 (titles) · `-2xl` 26 (welcome); weights `--weight-normal/medium/semibold/bold`. Line heights aren't tokenized (virtualized rows need exact heights).
- **Sizes**: controls `--control-xs` 20 · `-sm` 24 (icon/row buttons) · `-md` 28 (default buttons, inputs, selects) · `-lg` 32 (toolbar, palette search); rows `--row-md` 28 (all lists; keep the `ROW_H` constants in sync) · `--row-lg` 32 (pickers).
- **Colours** (surfaces pair with a `-foreground`): `--background`/`--foreground` (chrome, text) · `--surface` (panels) · `--surface-sunken` (inputs, headers) · `--overlay` (menus, popovers, dialogs; a touch lighter in dark themes) · `--muted-foreground` · `--subtle-foreground` · `--border` / `--border-strong` · `--primary` / `--primary-foreground` / `--primary-soft` · `--selection` / `--selection-strong` (unfocused / focused) · `--hover` · `--ring` (focus) · `--danger(-foreground)` · `--warning(-soft)` · `--diff-add`/`-gutter`/`-foreground`, `--diff-del…` · `--syntax-comment/keyword/string/number/function/type/property/tag` · `--graph-lane-0…7` · `--avatar-*`, `--brand-*`, `--shadow`, `--scrim(-soft)`. Selection/soft tints are `color-mix` of `--primary`, so a theme that changes only `--primary` stays coherent.
- If you know shadcn: `--background`, `--foreground`, `--primary(-foreground)`, `--muted-foreground`, `--border`, `--ring` mean the same; their `--card`/`--popover` ≈ our `--surface`/`--overlay`; `--destructive` ≈ `--danger`.

## Theming
Light palette on `:root, [data-theme='light']`, dark overrides on `[data-theme='dark']` (both in `tokens.css`; `[data-theme]` works on any element, which the Preferences theme previews use).
- `src/renderer/src/theme.ts`: setting (`system` | theme id, localStorage `theme`) → sets `<html data-theme>` to the base and applies a theme's overrides inline; follows the OS in system mode. `initTheme()` runs before the first render. Pickers: palette "Choose theme…", Preferences → Themes.
- Built-in themes (`builtInThemes.ts`) and custom themes are a base plus token overrides. Custom themes: JSON files in `<userData>/themes` (`{ "name", "base": "light"|"dark", "colors": { "primary": "#…", "background": "#…" } }`, keys are token names without `--`), loaded by `listThemes` in `src/main/windowTheme.ts`, cached in localStorage for the first paint. "Open custom themes folder" command.
- Native parts (title bar overlay, window background, `nativeTheme.themeSource`) follow through `api.setWindowTheme`; saved to `<userData>/window-theme.json` so the next launch starts in the right colours.

## Verifying changes (do this, don't guess)
- Demo repo with branches/merges/tag lives in the session scratchpad (`demo-repo`, bare remote `remote.git`); recreate with a few `git` commands if missing.
- Dev helper in `src/main/index.ts` (env vars, after `npm run build`):
  - `OAK_SCREENSHOT=<png>` capture and quit; `OAK_SCREENSHOT_DELAY=<ms>`
  - `OAK_SCREENSHOT_KEYS="Control+1,Down,Shift+Down,Return"` sends **real** keystrokes (also `Click@x:y`, `Shift+Click@x:y`, `RightClick@x:y`, `Wheel:<dx>:<dy>@<x>:<y>`); menus are DOM (`.menu-popover [role=menuitem]`), so inspect them with `OAK_SCREENSHOT_JS` and logs focused pane/row/selection after each (note: Enter on native buttons needs Space in this helper)
  - `OAK_SCREENSHOT_JS=<expr>` runs in the page; its result is printed
  - Keys are comma-separated, so Ctrl+, can't be sent; open Preferences via the palette instead
- Measure layout shift / padding with `getBoundingClientRect` sampling rather than eyeballing.
- Git-level behaviour: check with `git status/diff --cached` after driving the UI.

## Workflow with the user
- Website copy should be plain and descriptive: explain what Oak and its controls do. Avoid slogans, aspirational taglines and sales language. Showcase the command palette as a main feature, with concrete examples and shortcuts; do not claim features are exclusive without evidence.
- When presenting choices, include a clear recommendation and explain why. Oak's agreed focus is everyday Git with fewer distractions; website copy should demonstrate concrete behaviour, use factual language and avoid unsupported speed, superiority or uniqueness claims.
- **Local review before publishing:** prepare future changes locally, run the relevant checks, and give the user the commands/preview needed to review and test them. Wait for their explicit approval before releasing the app or deploying website changes. Successful automated checks do not count as user approval. Website pushes to `main` auto-deploy, so keep unapproved website changes local or on a feature branch; never push them to `main`, trigger website publication, push release tags or run `npm run release` before approval. Private backup pushes that cannot publish are allowed.
- **Build on the shoulders of giants:** before building a component, hook or behaviour from scratch, check React Aria Components / react-stately (docs: react-aria.adobe.com) and other established libraries; use them where they save time or read better. Hand-roll only when nothing fits (commit graph, diff), and say why.
- Work in milestones; stop for the user to test. Small, focused commits as you go (one-line messages, no trailers).
- Explain before changing when the user asks "why"; record ideas/investigations in `ROADMAP.md`.
